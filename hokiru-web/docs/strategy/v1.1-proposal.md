# v1.1 改善提案 — HOKIRU Web / AI副業ファクトリー

**作成: 2026-07-02｜作成者: Claude（Notion「AI副業 統合戦略ドキュメント v1.0」「HOKIRU（一級建築士 法規学習アプリ）」「HOKIRU 事前決定メモ」を読解の上で作成）**

本書はv1.0を置き換えるものではなく、v1.0への加筆修正案として運用する。Notion側の追記は
`docs/operations/notion-update-spec.md` の手順で行う。

## 1. v1.0の要点（要約）

- **現在の最大ボトルネック**: 技術力ではなく、公開品質に達するまでの反復回数を人間の可処分時間で
  賄えなかったこと。収益実績0円の根本原因はここにある。
- **HOKIRU Webを旗艦にする理由**: 「機械が無人で品質を上げられるか」を選定基準とし、実装→テスト→
  プレビューURL→スクリーンショット→PRの全工程を無人化できるのがHOKIRU（Web版）である。
- **iOSではなくWebに転換する理由**: iOSはビルド・スクリーンショット・審査がMacと人間の操作に
  依存し、夜間の無人反復の障害になる。Web（Next.js + Vercel）なら全工程が自動化できる。
- **人間に残すべき操作**: ①PRのマージ承認 ②判断キューへの回答 ③発信の送信 ④（将来）受験、の4つのみ。
- **自動化すべき操作**: 実装・テスト・スクリーンショット取得・PR作成・Notion進捗更新・判断不要な
  設計選択。
- **権利問題の扱い**: 過去問（R07法規120問）は資産として保持するが公開用データには使わず、
  「AI生成 × 一級建築士本人監修」のオリジナル問題に全面転換する。rightsStatusゲートで技術的に強制する。
- **資格学習ファクトリーとしての横展開方針**: HOKIRU Webを第1号機のテンプレートとし、次に取得する
  資格（診断士・マン管など）で第2号機を再現する。肩書きが増えるほど原料が増える複利構造。

## 2. 矛盾・不足・設計漏れの洗い出しと解決

| # | 論点 | 現状 | 解決方針（v1.1） |
|---|------|------|------------------|
| 1 | HOKIRUは「一級建築士法規」か「宅建」か | **方針ズレを確認。** 「HOKIRU 事前決定メモ」(2026-06-27作成)は「対象は、まず宅建受験者に絞る」と明記。一方でv1.0 (2026-07-01) は「一級建築士本人監修のオリジナル問題」と明記し、既存資産(R07法規120問=一級建築士法規)を引き継ぐ前提で書かれている。 | v1.0が事前決定メモより新しく、かつ既存資産(R07法規120問・一級建築士という肩書きそのもの)と整合するため、**v1.0を正とし、一級建築士法規を旗艦資格として確定する**。事前決定メモの「宅建」記載は執筆時点の暫定案として扱い、本書で上書きする。ただし宅建はシナリオA第2号機以降の横展開候補として保持する（宅建士の肩書きも保有資産にあるため）。 |
| 2 | 既存R07法規120問の扱い | 権利問題(rightsStatus=permittedAssumed)により公開ゲートで停止中。 | 公開用データには使わない。`data/internal/` に隔離し、**出題傾向分析・AI生成のプロンプト参考にのみ**使用可（生成物そのものをそのまま使わない）。rightsStatus=`third_party_restricted`または`internal_reference_only`として扱い、`canPublishQuestion()` で技術的に公開経路から排除する。 |
| 3 | AI生成問題の監修フロー | 未設計。 | `supervisionStatus`を`unsupervised → in_review → supervised`の3段階にする。AIが問題を生成した時点では`unsupervised`。人間(一級建築士本人)がレビューし`reviewedBy`+`lastReviewedAt`を埋めた時点で`supervised`に遷移。**`canPublishQuestion()`は`supervised`かつ許可された`rightsStatus`かつ法令根拠必須のときのみ`true`を返す。** 監修は「人間の専門性が必須な唯一の作業」(v1.0 Phase 1)として、判断キューではなく専用の監修キュー(dod.md Rights DoD)で管理する。 |
| 4 | Supabaseを初期から使うか | 未確定。 | **使わない。** MVPは匿名ローカル保存(localStorage)を既定とする。`lib/supabase/client.ts`・`server.ts`は用意するが、env未設定時はnullを返し優雅に縮退する。Supabase移行は「複数端末同期が要る」という具体的ニーズが出てから行う(過剰実装の回避)。 |
| 5 | ログインをMVPに入れるか | 未確定。 | **入れない。** 匿名ローカル保存のみ。将来Supabase匿名認証(`auth.signInAnonymously`)でクロスデバイス同期に拡張できるよう、データ形状(questionId起点)は最初から互換性を持たせる。 |
| 6 | Stripe課金をMVPに入れるか | 未確定。 | **入れない。** DoD完了後、Phase 2(公開)で導入。価格自体は判断キュー行き(§4)。 |
| 7 | Vercelプレビューとスクリーンショット取得の連携 | 未設計。 | `.github/workflows/screenshot.yml`(テンプレート)がPRごとにVercelプレビューURL(`BASE_URL`環境変数経由)に対してPlaywrightスクリーンショットを撮り、artifactとして添付する設計とした。Vercel初回接続は人間のPhase 0タスク。 |
| 8 | GitHub ActionsからClaudeを起動する方法 | 未設計。 | `.github/workflows/nightly-ai-dev.yml`(テンプレート)にcronトリガーと`ANTHROPIC_API_KEY`前提の起動ステップを用意した。Claude Code Action相当が使えない場合のフォールバック手順を`docs/operations/ai-nightly-run.md`に明記。 |
| 9 | Notion更新をどこまで自動化するか | 未設計。 | 直接更新(Notion API/MCP)が使える環境では`notion-update-page`等で直接追記。使えない環境では`scripts/notion-update-draft.ts`が貼り付け用Markdownを生成する二段構え。詳細は`docs/operations/notion-update-spec.md`。 |
| 10 | 判断キューの実体 | 未設計。 | **両方使う。** GitHub Issue(`needs-decision`ラベル)を一次ソースとし、Notion「判断待ち」セクションはその一覧のミラー(人間がスマホで見るため)とする。 |
| 11 | 夜間ラン失敗時の復旧設計 | 未設計。 | `docs/operations/ai-nightly-run.md` §失敗時の行動を参照。直せない場合はブランチとPRを残さず、失敗記録をIssueに残して次回に持ち越す(中途半端なPRを積まない)。 |
| 12 | Claude使用量が不足した場合の縮退運用 | 未設計。 | `docs/operations/token-budget.md`。夜間ランを間引き、対話利用を優先する。 |
| 13 | 法令・資格情報の更新責任 | 未設計。 | 一級建築士本人(人間)の責任範囲として明記。AIは法改正を検知して`needs-decision`(法令更新レビュー)を起票するだけで、法的判断は行わない。 |

## 3. 旗艦プロダクトの確定案

- **プロダクト名**: HOKIRU Web（暫定）
- **旗艦資格**: 一級建築士法規（v1.0を正とし、事前決定メモの宅建記載を上書き。詳細は上表#1）
- **コア価値**: 「忘却の可視化」と「復習自動化」
- **横展開の型**: 《取得実録note ＋ AI生成問題の学習アプリ ＋ 発信》を1セットとするテンプレート。
  次の号機は宅建・診断士・マン管など、実際に取得する資格から選ぶ。

## 4. MVPスコープ / 非MVPスコープ

詳細は `docs/product/mvp-scope.md` / `docs/product/non-mvp.md` を参照。要点のみ:

- **MVPに入れる**: 演習・復習・分析・設定の4画面 + ホーム、rightsStatusゲート、匿名ローカル保存、
  復習スケジューラー、法令根拠表示、監修ステータス表示。
- **MVPに入れない**: 課金、ログイン/複数端末同期、コミュニティ、高度なAI診断、通知、複数資格同時対応。

## 5. 自動運用アーキテクチャ

```
GitHub Actions (cron, 平日深夜)
  └─ nightly-ai-dev.yml
       1. docs/operations/dod.md を scripts/collect-dod-status.ts で解析
       2. needs-decision の項目を除外
       3. 依存の少ない1件を選定
       4. 作業ブランチを作成
       5. 実装
       6. lint / typecheck / test
       7. Playwright スクリーンショット取得
       8. 失敗したら自己修正、直らなければ失敗記録を残して終了
       9. PR作成（テンプレートに沿った本文）
       10. Notion更新 or notion-update-draft.md 生成
       11. 判断が必要なものは create-decision-issue.ts で Issue化

screenshot.yml … PRごと / 手動でスクリーンショットartifact生成
ci.yml         … PRごとに lint/typecheck/test/build/e2e
notion-sync.yml … Notion直接更新 or draft artifact化
```

人間の操作: PRのスクリーンショットを見てマージ or 差し戻し、Issueの`needs-decision`に回答、
発信下書きを送信するのみ。

## 6. DoDの詳細化

`docs/operations/dod.md` に12カテゴリで細分化済み(Product / UI / Learning Experience / Question
Quality / Rights / Technical / Test / Accessibility / Performance / Security / Operations /
Release)。各項目はAIが1項目ずつ独立して消化できる粒度にした。

## 7. リスクと対策

| リスク | 対策 |
|--------|------|
| AI生成問題に法令の誤りが混入する | `supervisionStatus`ゲートで人間監修必須化。誤りが1件でも見つかれば該当問題を`unsupervised`へ差し戻す運用ルールをdod.mdに明記。 |
| 夜間ランが同じ失敗を繰り返す | 失敗記録をIssueに残し、次回ランは同一項目を連続実行しない(履歴参照)。2回失敗したらneeds-decision化。 |
| 判断キューが溜まって停滞する | 判断不要のタスクは並行して進む設計(pull型)。停滞はDoD残数の可視化で検知する。 |
| Claude利用量の枯渇 | token-budget.mdの縮退運用(夜間ラン間引き)。 |
| 権利ゲートのすり抜け | `canPublishQuestion()`を唯一のゲートとし、UI・seed・LPすべてがこれを経由する設計をtestで固定(`tests/unit/rights.test.ts`)。 |
| Web版がiOS版ユーザーの期待を裏切る | iOS版は「延命しない」と明言し、Web版への移行メッセージを利用規約/LPで明確化(Release DoD)。 |

## 8. 人間がやるPhase 0

`docs/operations/release-process.md` の Phase 0 セクションと同一。要約:

- 認証情報のパスワードマネージャ移行
- claude.aiでの定時タスク（毎朝ループ・週次レビュー）設定
- GitHub Actions初回認可・secrets登録
- Notion API連携の認可
- Vercel・Supabaseの初回接続
- PRの最終マージ判断
- 監修済み問題として公開する最終判断

## 9. AIがやるPhase 1以降

- DoD残数を夜間ランで消化し続ける
- AI生成問題のドラフト作成（監修は人間）
- スクリーンショット・PR・Notion進捗更新の無人実行
- 判断が必要な項目のIssue化

## 10. 30日以内の到達点
